# Threat model (MVP)

Scope: a demo with synthetic data. It shows the controls a real deployment would need, but it is not HIPAA-compliant: no encryption at rest, retention policy, audit trail or real identity provider.

The Java server validates the ID format.                                                                                                                                                                                     | `ehr.test.ts` (override, fail closed); `api.test.ts` (the placeholder resolves to the right patient); `spike:mcp`         |
| Missed red flag                                         | `safety_gate` is deterministic and runs first. ## Known gaps

- **No rate limiting.** Anyone with a token can send messages as fast as they like.
- **No audit trail** of who read or resolved what, beyond opaque-ID log lines.
- **One instance only.** The per-thread lock and the SQLite file assume a single process.
- **A failed turn keeps the patient's message.** If the model is down, the message stays in the thread and a retry adds it again.
- **Demo authentication.** Anyone can sign in as any seeded patient or as a nurse. The signing secret lives in an environment variable.
- **The sign-in token sits in the browser's `sessionStorage`.** Script injected into the page could read it. The portal renders all text as text and never uses `dangerouslySetInnerHTML`, but a real deployment should use an HttpOnly cookie with CSRF protection.
- **No CORS and no Content-Security-Policy.** The API expects a same-origin reverse proxy (Vite's proxy in development). A production deployment needs the proxy and a CSP.
- **Clinical content is unreviewed.** The red-flag patterns, the emergency text and the demo model's replies need clinical review before any real use.
